# TDD Rule

> **⚠️ 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나, 순서를 바꾸거나, 예외를 스스로 만들지 않는다.

## 0. 우선순위 (프로젝트별 규칙 우선)

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
- 충돌 시 프로젝트 규칙을 따르고, 이 파일의 해당 부분은 무시한다.

## 1. 적용 기준

### 반드시 TDD 적용

- **비즈니스 로직**
- **API** (엔드포인트, 핸들러, 클라이언트 호출 로직)
- **유틸리티 함수**
- **버그 수정** (재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- **타입 정의** (`type`, `interface`)
- **설정 파일** (`vite.config.ts`, `tsconfig.json`, `eslint.config.js` 등)
- **순수 UI** (로직 없는 마크업/스타일링)
- **SQL** (스키마, 마이그레이션)

판단이 애매하면 **적용 대상으로 간주**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니므로 고친 뒤 다시 실행한다.

### GREEN — 통과시키기

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 분기, 확장 포인트를 추가하지 않는다.
- **신규 + 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 재시작한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 보면서 다시 쓰기 모두 포함한다.
- 삭제 후에는 테스트부터 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 30초면 끝난다. 단순한 코드가 가장 자주 깨지고, 테스트가 없으면 깨진 줄도 모른다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰 작성되어 **바로 통과**한다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 TDD보다 오래 걸린다. 급할수록 **테스트가 시간을 번다.** |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 적용 대상이 아니라고 **사용자가 명시**해야 한다. 스스로 판단하지 않는다. |
